# Report 2026-10-21: Mach3Step and DMR on the RPTU cluster (MUSCL3 / MUSCL4, MLS order)

All runs: Mach3Step (t = 4, R = 2.5, jitter 0.2), Float32, RK + MUSCL + MOOD U2 (`MOOD_delta_relax = 0`), on the
cluster through the Slurm gateway, one method per job (`cluster/run_method.sh`). Registered packages
(HyperCloud 0.4.0, HyperCloudCore 0.6.2, both with the PAD of MOOD), CUDACore from CUDA.jl main.

"Mass" below is the `mass drift` of the run summary: total mass at t = 4 relative to t = 0. Mach3Step has an inflow
and an outflow, so this is **not** a conservation error by itself; but all conservative variants (fixed MLS order)
agree on it to 1e-3 at every resolution, so the difference to them ("Δmass", relative to the final mass of the
RK2MUSCL2(EPD1) reference at the same resolution and CFL 0.8) is a usable measure of the conservation error.

## 2. Findings

1. **Fixed MLS order 3 (MUSCL3) and 4 (MUSCL4) blow up immediately**, independent of the CFL (same physical time
   t ≈ 0.036 at CFL 0.4 and 0.1, so not a time step problem). The negative pressure starts at x = (0.586, 0.001), the
   concave corner between the bottom wall and the step front (stagnation point of the inflow). PAD in MOOD does not
   help: with a fixed divergence degree the order-1 fallback is not the first-order scheme (cubic MLS divergence
   with first-order fluxes, see REPORT_2026-10-17 §3), so lowering the order cannot restore positivity.
2. **MLS order 0 with EPD1 gains ~8–10 % mass** (relative to the conservative runs) at every resolution
   (600×200 … 1200×400); it does not converge away, and it depends on the CFL (+9.8 % at 0.4, +7.7 % at 0.8). It
   also has the lowest pressures (min p 4.4e-5 at 1200×400, close to failing). Likely cause: with MLS 0 every
   particle's divergence degree follows its *own* MOOD order, EPD1 only aligns the two orders at an interface, so
   neighbours i, j with k_i ≠ k_j use different divergence stencils and the antisymmetry of the fluxes is lost.
3. **MLS order 0 with EPD2 is much closer** (−0.6 … −3.2 %, a loss, not a gain): EPD2 lowers the whole
   neighbourhood, so mismatched neighbours are rarer. Still not conservative, and also CFL dependent.
4. **MUSCL4 with MLS 0 (EPD1) is the most conservative MLS-0 variant** (−1.2 % at 600×200, −0.5 % at 900×300) and
   stable at CFL 0.8, but about 3× the steps of MUSCL2 and ~14× its runtime (112 vs 8 min at 900×300 on a V100).
   1200×400 would take ~5 h on a V100 (over the 300 min limit, not run).
5. **MUSCL3 with fixed MLS 2 is conservative and robust, but it is essentially MUSCL2**: the same number of steps
   as RK2MUSCL2 (the CFL uses the divergence coefficients, and MLS 2 means the degree-1 divergence of MUSCL2) and
   nearly the same min p and mass at every resolution. By the HyperCloudCore docs, MUSCL3 needs the degree-3
   divergence for third order, so with MLS 2 it is a second-order scheme with a quadratic reconstruction. It was
   the only MUSCL3 variant that fits 1800×600 into the time limit.
6. **CFL 0.8 is fine for every stable variant** (MLS 2: identical results to 0.4; MLS 0: different but not worse
   min p), which halves the cost compared with 0.4.

So on this problem: no MUSCL3/MUSCL4 setting is both conservative and positive with the current library. The fixed
order conserves but the fallback is not positive (fails at the corner); the coupled order is positive but loses
or gains mass, least so for MUSCL4 and EPD2. A fallback that is first order *and* conservative would need the
neighbours of a dropped particle to use the same (lowered) divergence stencil for the shared interface, which is
what EPD2 approximates.

## 2b. DMR (MUSCL4)

DMR (t = 0.2, 3.2 × 1, R = 2.5, jitter 0.2), Float32, CFL 0.8, MOOD U2. "mass" is the summary `mass drift` (the
domain gains mass through the post-shock inflow), Δmass as above relative to the RK2MUSCL2(EPD1) reference at the
same resolution. The summary prints 3 digits, so Δmass has a resolution of ~0.25 %.

| RK4MUSCL4(EPD1) | **4** | blows up at t = 0.0099, x = (0.299, 0.001) | – | – | – |
| RK3MUSCL3(EPD1) (for comparison) | 0 | 3.19 (+3.5 %) | – | – | – |

- All runs except the fixed MLS 4 reach t = 0.2 with positive pressure (min p = 1, the pre-shock state, except
  EPD2 at 1920×600: 0.987 behind the shock); positivity is not the issue on DMR.
- **Fixed MLS 4 fails like on Mach3Step**: at the bottom wall where the incident shock reflects at that time
  (shock foot at x ≈ 1/6 + 20t/√3 = 0.28), again a wall/stagnation point.
- **MLS 0 gains mass, and the gain does not shrink with the resolution** (+5.4 % at 960×300 and 1440×450, +5.7 % at
  1920×600 for EPD1; +2.2 … 2.5 % for EPD2; MUSCL3 EPD1 +3.5 %). On Mach3Step EPD1 also gained (+8 … 10 %) but EPD2
  lost (−0.6 … −3 %). A conservation error from MOOD order changes at shocks should shrink with h (the
  flagged region is a fixed number of particles across the shock, so its area shrinks); a resolution-independent
  error points to a permanent source with an O(1) rate, e.g. particles whose order is permanently lowered along a
  boundary (the pre-gather pass sets the order to 1 where a stencil is too small) next to interior particles with
  a higher-degree divergence. Not verified: a run with MLS 0 on a smooth problem with walls (no MOOD activity)
  would separate the two.
- **MUSCL4 with fixed MLS 2** is conservative, stable and about 3× cheaper than MLS 0 (5887 vs 15999 steps at
  1920×600), but like MUSCL3 with MLS 2 on Mach3Step it uses the degree-1 divergence of MUSCL2 (steps ≈ MUSCL2),
  so it cannot be fourth order.
- Runtimes (1920×600): MUSCL2 EPD1 11 min (V100), VK 4.5 min (V100 DGX), MUSCL4 MLS 2 64 min (V100), MUSCL4 MLS 0
  EPD1 187 min / EPD2 235 min (V100 PCIe, gpu004).

  cheaper than MOOD (fewer recomputations) but BJ reaches the lowest pressure (0.005) at the corner.
- Upwind1 is very diffusive (min p 0.76 vs 0.02–0.2) but costs as much as BJ/VK.

## 3. Venkatakrishnan / Barth-Jespersen limiter crashes on CUDA (fix verified, not in the package)

`RK2MUSCL2(VK)` fails on every NVIDIA GPU with `Out of dynamic GPU memory (trying to allocate 16 bytes)` in
`_rhs_gather!`. Cause: `_limit_slopes` for BJ/VK (`src/Interpolation/Limiter.jl`) builds `u_max`, `u_min`,
`phi_i` as `MVector`s and captures `phi_i` in the final `ntuple` closure, so it is heap allocated; on CUDA that is
a device `malloc` per call until the (8 MB) device heap is gone. `cluster/patches/limiter_nomvector.jl` redefines
it with `SVector`s only (`max.`/`map`, closures only over variables assigned once):

- CPU, 150×50: bitwise identical summary with and without the patch (and slightly faster).
- CUDA, 600×200: the run completes and is identical to the CPU run (17744 steps, same min p and mass).

To use it in HyperCloudCore, replace the BJ/VK `_limit_slopes` with the function body of the patch.

## 4. Running things on the cluster (for later)

- Order: `slurm instantiate env_headless env_cuda` (syncs first; without arguments it also instantiates
  env_local/env_web/env_gpu) → `slurm submit …`. A plain `slurm sync` uploads the local Manifest, so keep a local
  one (`julia --project=. -e 'using Pkg; Pkg.instantiate()'` in the repo root, gitignored); without it the
  cluster loses its Manifest and jobs fail at `using`.
- `slurm submit cluster/run_method.sh gpus=1 cpus=4 mem=48 time=300 -- Mach3Step <key> <Nx> <Ny> <CFL> [cpu|cuda] [Float32|Float64] [g2,vkpatch]`;
  keys: m2, m2vk, m3, m3epd2, m3mls2, m3mls3, m4, m4mls4 (see the script).
- `slurm fetch <jobid>` downloads the job's `*.jld2` to `data/<jobid>/` (gitignored); all runs of this report
  are fetched there (`job-info.txt` next to each file has the sacct line). The cluster copies are deleted after
  14 days (`RUNS_KEEP_DAYS`).
- `gputype=` works for v100, a40 (gpu009), b200 (dgx005, partition b200idle). **a30 nodes failed** at `using
  CUDACore` ("CUDA.jl's JLLs were precompiled without an NVIDIA driver present" → `libcudart not defined`):
  the gateway's instantiate precompiles on the login node (EPYC 7262, no GPU) into the shared depot, and the A30
  nodes have the same CPU type, so they reuse that cache (the Xeon nodes compile their own with the driver
  present and get runtime 12.9 on the 13.0 drivers, 13.4 on the 13.3 drivers). The `CUDA_Runtime_jll` version
  preference was 12.6, which this jll does not ship, so it was ignored. Fixed: pinned to **12.9** and
  `CUDA_Runtime_jll` listed under `[extras]` of Project.toml and env_cuda/Project.toml (Preferences.jl only
  applies preferences of packages listed in the environment). Verified on an A30 node (job 24539615: runtime
  12.9 on the 13.3 driver, same results as on the V100). The `dgx` partition is refused by the
  cluster ("not entitled"); A100/H100 in gpuidle were busy for hours.
- Compiled package images are per CPU type (`cluster/common.sh`): EPYC and Xeon nodes overwrote each other's images
  in the shared depot before.
