## 3. clainshock4 (4th order, "does not converge"): root cause found and fixed (on branches)

Before the fix, RK4 MUSCL4 EPD1 on clainshock4 ended with **negative pressure at every CFL tried** (0.01, 0.05,
0.1, 0.2, 0.4, 0.8; 100², Float32 and Float64), so CFL is not the knob. Two causes:

1. **The fixed divergence order is not capped by the MOOD order** (`HyperCloudCore/src/Interpolation/MUSCL.jl`,
   `_resolve_div_idx(::Val{DO}, p_order) = max(2, DO)`). With `MLS_order = 4`, a particle MOOD dropped to order 1 gets
   first-order fluxes under a *cubic* MLS divergence: not the first-order scheme, not positivity preserving. On a
   symmetric stencil a quadratic fit gives the same gradient as a linear one, which is why MUSCL2/3 are unaffected and
   MUSCL4/5 are. Diagnosis (`tools/debug/compare_rhs.jl`): the RHS of an order-1 particle equals the MUSCL1 RHS for
   MUSCL2/3 (to 1e-10) but is completely different for MUSCL4/5. `UpwindDivergence` already caps it
   (`min(DIV_ORDER, p_order)`).
2. **MOOD has no physical admissibility detection (PAD)**: the criteria are a DMP on the conserved variables only, so a
   negative pressure with conserved variables inside the local bounds is accepted; a NaN candidate also passes (every
   comparison with NaN is false).

**Update after review:** the cap in (1) coupled a fixed MLS order to the MOOD order, which defeats the fixed order
(conservation). It is removed from `claude/mood-pad`; the branch now only adds the PAD:
- HyperCloudCore `claude/mood-pad` (worktree `/workspace/worktrees/HyperCloudCore-pad`): `is_admissible(eq, U)` API
  (default: finite), checked in `_mood_flag!`, with a test.
- HyperCloud `claude/euler-pad` (worktree `/workspace/worktrees/HyperCloud-pad`): `is_admissible` for conservative
  Euler (ρ > 0, p > 0, finite) + test. Needs the HyperCloudCore branch (new API), so it needs a HCC release first.

`MLS_order = 0` still couples both as intended (`_resolve_div_idx(Val(0), p) = max(2, p)`), so the 600² runs below
(made with the cap, identical to `MLS_order = 0` for MUSCL4) stand for **`MLS_order = 0` + PAD**: positive pressure at
CFL 0.2, 0.4 and 0.8 (EPD1 min p 6.7e-5 / 7.2e-3 / 1.5e-2; EPD2 at 0.2 and 0.4, min p 0.023). Relative L1
difference of ρ vs CFL 0.2: 1.2e-2 (0.4), 2.7e-2 (0.8). With the fixed `MLS_order = 4`, PAD alone still ended
negative at 100² (min p −1.4e-3), so the fixed order and a positive fallback are in conflict.

Conservation vs boundedness (`tools/debug/conservation.jl`: periodic 2-D advection of a box, RK4 MUSCL4 MOOD EPD1,
100², R = 5.5, t = 0.5, relative change of Σ V_i U_i):

| Grid | MLS order | mass change | min / max (exact: 0 / 1) |
|---|---|---|---|
| regular | fixed 4 | −1.8e-14 | −0.105 / 1.188 (no MOOD: −0.111 / 1.186) |
| regular | 0 (coupled) | **+9.3e-3** | −1.3e-6 / 0.997 |
| jittered 0.2 | fixed 4 | −0.135 | −0.085 / 1.176 |
| jittered 0.2 | 0 | −0.136 | −2.4e-6 / 0.995 |
| jittered 0.2, no MOOD | either | −0.134 | −0.093 / 1.176 |

So your point holds on the regular grid: the fixed order conserves exactly with MOOD, the coupled one does not. But
with the fixed order the MOOD fallback does not bound the solution (over/undershoots as without MOOD), because the
order-1 particles keep the cubic divergence. And on jittered grids **every variant loses ~10–13 % of the mass**, also
first order without MOOD (MUSCL1: −9.8 % at 100², −7.2 % at 200², nearly independent of the jitter size 0.05–0.2).
The semi-discrete residual Σ V_i K_i (one RHS evaluation) is 1e-17 on the lattice and ~1e-3 of Σ|V_i K_i| already at
1 % jitter. Two contributions: the exponential weight is not zero at the cutoff (w(R) = 0.37 for α = 1), so a tiny
jitter moves neighbours in and out of the support with a jump (α = 4 reduces the residual at 1 % jitter 70×), plus
the general asymmetry c_ij V_i ≠ −c_ji V_j of MLS stencils on irregular points (grows with jitter). Not pursued.

## 4. CFL: 0.2 is very conservative

`dt = CFL / (D · Σ_k |c_k| · λ_i)` (MLS divergence coefficients), so the number is not a classical Courant number (explanation added to the HyperCloudCore docs, branch `claude/cfl-docs`: first-order forward Euler with Rusanov is invariant-domain preserving for CFL ≤ D under symmetric-stencil assumptions): on
DMR 960×300 CFL 2.0 is a classical λ·dt/dx ≈ 0.63, on Euler2D 400² CFL 1.0 ≈ 0.3.

| Problem | Methods | Runs fine up to | Breaks at | Rel. L1(ρ) vs CFL 0.2 at CFL 1 / 2 |
|---|---|---|---|---|
| Euler2D 400² (RK2) | VK, EPD1, EPD2, Upwind1 | 3.0 | 4.0 (2 steps) | VK 2e-5 / 1.3e-4, EPD 4e-3 / 7e-3, Upwind 1e-5 / 2e-5 |
| DMR 960×300 (RK2) | same | 2.0 (highest tried) | – | VK 1e-4 / 2.6e-4, EPD 2e-3 / 4e-3, Upwind 6e-5 / 1e-4 |
| Mach3Step 600×200, t = 4 (RK2) | VK, EPD1 | 0.8 (highest tried) | – | at 0.8: VK 6e-5, EPD1 5e-3 |
| Sod 1-D, 330 (RK2 / RK4) | Upwind1, MUSCL2 EPD1/EPD2/VK/minmod, MUSCL4 EPD1 | 1.2 | 1.5 (VK and minmod still OK) | L1 error vs exact 1.0e-2 → 1.04e-2 (VK, 0.2 → 1.0) |
| 1-D advection, RK4 MUSCL2..5 (Float64) | | 1.5 (MUSCL2) .. 3.0 (MUSCL5) | 2.0 .. 4.0 | errors unchanged up to CFL 1 |
| clainshock4 600², RK4 MUSCL4 (fixed library) | EPD1 | 0.8 | – | 1.2e-2 at 0.4, 2.7e-2 at 0.8 |

The differences between CFL values are far below the discretisation error (EPD variants change by a few 1e-3 because
MOOD decisions shift). **CFL 1.0 is safe on every shock problem tried (5× fewer steps than 0.2); ~0.5 in 1-D.**

## 5. Convergence studies (Float64; 1-D on CPU, 2-D on GPU)

| | MUSCL2 | MUSCL3 | MUSCL4 | MUSCL5 |
|---|---|---|---|---|
| 1-D advection (N ≤ 3163) | 2.00 | 2.00 | 4.0–4.1 | 4.2–4.8 (pre-asymptotic) |
| 2-D advection, width 2 (as configured) | 1.9 | 1.9 | **1.6** | **1.5** |
| 2-D advection, width 1 | 2.06 | 2.07 | 4.03 | 4.4–4.9 (2e-7 at 1000²) |
| 2-D Burgers, width 2 (as configured) | 2.05 | 2.05 | 1.6 (4.1 before N≈250) | 1.6 |

- **The 2-D convergence configs use `IC_width = 2.0` on [-5, 5]²**: the Gaussian is 1.9e-3 at the periodic boundary
  with a derivative jump, which caps the 4th/5th-order convergence at ~1.6 below an error of ~1e-4 (advection) / 1e-5
  (Burgers). With width 1 (as in the 1-D config) MUSCL4 converges at 4.03 down to 6e-7 on 1000². Now set to 1.0 in both
  configs (commit 9a1fb8e).
- MUSCL3 is only 2nd order in 1-D and 2-D; MUSCL5 reaches 4.4–4.9, not 5 (odd orders lose up to one order). Possibly inherent
  to the midpoint-flux formulation, not investigated.
- 1-D: error floor ~5e-8 for MUSCL4/5 at N ≥ 2000, independent of CFL (so not time error); likely rounding in the
  MLS fits, not investigated.
- Step counts: the 2-D sweep runs at MUSCL4/5 need 1736 steps vs 651 for MUSCL2/3 at the same CFL, because the
  CFL coefficient sum uses the degree of the divergence.

## 6. GPU / platform observations

- **Multi-run processes on the GPU are unreliable** (the known AMDGPU 2.9.1 issue, now seen *without*
  `set_memory_limit!`): (a) DMR RK2Upwind1, 4th run in a process, blew up at t = 0.0059 in Float32; the same run alone
  or in a fresh process was fine (3/3), CPU Float32 too. (b) ConvergenceAdvection sweeps (16 runs per process):
  `GPU Kernel Exception: Unknown exception` in `_cfl_body!` in 2 of 4 processes, at different runs, gone on rerun. So
  `tools/run_batch.sh` runs one method per process and retries once; a reproducible failure fails twice.
- A blown-up run still "completes": `solve_equation` breaks out when `dt <= 1e-12` and the data is saved as a normal
  result (the CFL 4 runs: `t = 0.0037 / 0.3`, ρ = -7.6e6, no NaN). `tools/run_sim.jl` flags it (final time < tmax,
  |u| > 1e6, ρ or p ≤ 0); the runner should probably error or warn there.
- The `mass` statistic on particle data is not a usable conservation check: it differs by ~1–2 % between point clouds
  of the same problem.
- HyperCloudCore "Threaded loops do not allocate" (ThreadsBackend, `< 256 KiB`) failed twice at 284 KB under load
  and passed on rerun: a borderline threshold.
